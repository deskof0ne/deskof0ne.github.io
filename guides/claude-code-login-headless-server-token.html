Claude Code login on a headless server: login, token, API key

Three ways to authenticate on a VPS, how to tell which one is active, and what auth status does not prove.

The usual first problem with Claude Code on a remote machine is not the install, it is the login. A VPS has no browser, a scheduled job has no keyboard, and a container starts empty every time. This guide covers the three ways to authenticate on a server, how to check which one is actually in use, and one trap that quietly changes how you are billed. Everything below was checked against version 2.1.331 in a clean, empty home directory.

Option 1: interactive login over SSH

For a server you sit at, the simplest path is the normal login:

claude auth login

The flags from claude auth login --help: --claudeai (Claude subscription, the default), --console (Anthropic Console, billed by API usage), --sso and --email <email> to prefill the login page. On a machine without a browser, the CLI cannot open one, and the binary contains the fallback text "Browser didn't open? Use the URL below to sign in": you open that URL on your laptop, sign in there and paste the code back into the terminal on the server. The login is stored under the user's home directory (~/.claude), so it belongs to that Linux user only.

Option 2: a long-lived token for scripts and CI

A browser round trip makes no sense for a nightly job. claude setup-token is described by its own help as "Set up a long-lived authentication token (requires Claude subscription)". Run it once on a machine where you can sign in; it shows the token, and the CLI tells you to store it securely. Then give that token to the job through the environment variable CLAUDE_CODE_OAUTH_TOKEN:

# /etc/claude-work.env   (owner root, mode 600)
CLAUDE_CODE_OAUTH_TOKEN=paste-the-token-here
# in the systemd unit
EnvironmentFile=/etc/claude-work.env

Treat the file like a password: root-owned, mode 600, not in the repository, not in the script, not on the command line (a command line is visible to every user through ps and ends up in logs).

Option 3: an API key

If you pay per token through the Anthropic Console, set ANTHROPIC_API_KEY in the same way, through an EnvironmentFile= or a secret store. This is also the right choice when several people or machines share a budget that you want to track separately from a personal subscription.

Check which login is active

claude auth status prints JSON by default; --text gives plain text. The exit code is usable in a script. In an empty home directory without any credentials:

$ claude auth status --text
Not logged in. Run claude auth login to authenticate.
$ echo $?
1

With an environment variable set, the same command reports it as the source. With CLAUDE_CODE_OAUTH_TOKEN set it printed Auth token: CLAUDE_CODE_OAUTH_TOKEN; with ANTHROPIC_API_KEY set, the JSON output showed "authMethod": "api_key" and "apiKeySource": "ANTHROPIC_API_KEY".

Two traps worth knowing

  • auth status does not test the credential. It reported "loggedIn": true for an obviously fake key. It tells you what is configured, not whether it works. The real test is a cheap call: claude -p "say ok" --max-budget-usd 0.1. With the fake key it ended with "Invalid API key" and exit code 1. Make your monitoring run a call like this, not only the status command.
  • An API key in the environment wins. On a machine that was logged in through the subscription, setting ANTHROPIC_API_KEY switched the reported method to api_key. Even with both CLAUDE_CODE_OAUTH_TOKEN and ANTHROPIC_API_KEY set, the key was reported as the source. A forgotten key in a profile file, a unit or a container image therefore sends usage to API billing instead of the subscription you thought you were using, and nothing warns you. If something is billed unexpectedly, run claude auth status as the user and in the environment of the failing job, not in your own shell.

Common failures on a server

  • Works in your shell, fails in the timer. The unit runs as another user or with a minimal environment, so neither your ~/.claude login nor your exported variables exist. Provide the credential through the unit's EnvironmentFile= or log in once as that user.
  • Login expired. The status output of a subscription login shows when the sign-in ends. Put that date in your calendar, or use the long-lived token for unattended work.
  • Token pasted into a script or a shell history. If a credential has appeared anywhere visible, replace it. Deleting the line does not remove the copy in a log.
  • Shared accounts. A login in a user's home directory is available to everything that runs as that user, including any program an agent starts. Use a dedicated user for the agent and keep your own credentials out of its reach.

A short checklist

  • Interactive server: claude auth login, open the URL on another machine, paste the code back.
  • Scheduled job: claude setup-token once, token in a root-owned mode-600 environment file.
  • Know the source of the credential: claude auth status --text as the user that runs the job.
  • Test with a tiny paid call and a budget cap; auth status alone proves nothing.
  • Search profiles, units and images for a stray ANTHROPIC_API_KEY.
