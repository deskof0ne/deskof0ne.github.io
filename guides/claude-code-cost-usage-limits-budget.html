Claude Code costs: see usage, keep context small, cap spend

Where the tokens go, the commands that keep a session cheap, and a hard cap for scheduled runs.

Claude Code bills by tokens, either against a subscription plan's limits or per token through an API key. Either way, a few habits decide whether a session stays cheap or quietly burns through your allowance. This guide shows how to see what a session costs, the three things that make it grow, and how to put a hard cap on unattended runs. Commands and flags are from Claude Code 2.1.x; check claude --help and /help on your version.

See what you are spending

Inside a session, /usage shows the session cost, your plan usage and what is contributing to your limits. /cost and /stats are aliases for the same command. Look at it after a long task, not only when a limit warning appears.

For a bounded non-interactive run, ask for JSON and read the cost from the result:

claude -p "summarize the failing tests" --output-format json | jq '.total_cost_usd'

The result object carries a total_cost_usd field, so a wrapper script can log what every scheduled run cost.

Why a session gets expensive

  • Context grows with every turn. Each new message is sent together with the whole conversation so far. A late question in a long session costs far more than the same question in a fresh one. /context draws the current context usage as a grid, so you can see how full it is.
  • Big tool output. A command that prints thousands of log lines puts all of them into the context. Filter first: tail, grep, head, or ask Claude to search instead of dumping a file.
  • The model and effort setting. A larger model with high effort is the right tool for design and hard debugging, and wasted money for renaming a variable.

Keep the context small

  • /clear starts a new session with empty context. The previous one stays on disk and can be resumed with /resume. Use it whenever the topic changes.
  • /compact frees up context by summarizing the conversation so far. Use it when you continue the same task but the history has become long.
  • Put stable rules in CLAUDE.md instead of repeating them in chat, and keep that file short; it is read at the start of every session.
  • Hand a broad search ("where is X used?") to a subagent. It reads many files in its own context and only the answer comes back.

Pick model and effort on purpose

/model sets the model and /effort sets the effort level for the session. On the command line the same are --model (an alias such as sonnet or opus, or a full model name) and --effort with one of low, medium, high, xhigh, max. A sensible default: a mid-sized model with medium effort for routine work, the larger one for planning and hard problems.

A hard cap for unattended runs

For jobs that run without you, --max-budget-usd sets the maximum amount to spend on API calls. It only works together with -p (print mode):

claude -p "run the nightly checks and report" \
  --max-budget-usd 2.00 \
  --output-format json

When the cap is reached the run stops and the JSON result reports a budget-exceeded error subtype instead of a normal result, so a wrapper should check the exit status and the result before treating the run as successful. Combine the cap with a narrow --allowedTools list; the cron and systemd guide shows the full setup.

A short checklist

  • Check /usage after every long task.
  • /clear on a topic change, /compact when the same task runs long.
  • Filter command output before it reaches the context.
  • Match model and effort to the task.
  • Every scheduled claude -p run gets --max-budget-usd and a log of total_cost_usd.
